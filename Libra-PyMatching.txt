Libra with PyMatching assignment
==============================

This report documents the new implementation and repeats the accuracy
measurements for that implementation. The earlier Libra.txt remains a record
of the original Blossom V assignment backend. Existing project files and all
13 source files in the saved original Libra manifest were preserved.

Build: libra_pymatching/CMakeLists.txt. Link libra_pymatching_decoder, which
implements the existing dec::Libra API, instead of libra_decoder. Do not link
both implementations. See libra_pymatching/README.md for commands.
New implementation: src/decoder/libra_pymatching.cpp.
Assignment helper: src/decoder/libra_assignment_pymatching.h.

The distance 17 evaluation survived a daemon restart and continued writing
its original progress log. A duplicate started during recovery was stopped
during initialization; its partial artifacts were preserved and none of its
samples are used here. All accuracy tables use completed production outputs.

1. Blossom V is optional
-----------------------

Libra does not require Blossom V. The main correlated detector-graph decodes
already used PyMatching. Blossom V was used only for an auxiliary assignment:
cover each selected CSS graph edge exactly once, with either an independent
single channel or a correlated channel covering two graph edges. That graph
already has explicit costs; its Blossom V solve used no Dijkstra preprocessing.

The new implementation uses exact subset dynamic programming for auxiliary
blocks of at most eight vertices and PyMatching for larger blocks. Existing
one- and two-vertex shortcuts remain. There are no Blossom V symbols in the
new Libra archive. The unchanged project still builds/links Blossom V for
its other decoders; this Libra implementation makes no calls to it.

Firing all assignment vertices in an unmodified PyMatching graph would
enforce odd parity, which can permit degree three and give the wrong cover.
For example, a four-vertex star with singles costing 10 and pairs costing 1
has a parity solution costing 3 but an exact cover costing 21.

Instead, quantize original costs to 1e-6, set C=1+max(single_cost), add boundary
edges C+s_i and pair edges 2C+p_ij, then fire all vertices. At a vertex of
degree>=3, removing two incident pair edges and toggling the boundary edges
at their other endpoints preserves parity and decreases cost by at least
2C-s_a-s_b>0. Thus every optimum has degree one. The added n*C cost is constant
on exact covers, preserving the original optimum. Doubled integer weights
make Sparse Blossom collision times integral. Large-block edge overflow is
rejected instead of silently changing precision. Dominated/parallel pairs
are pruned while retaining a cheapest original channel.

All optimal assignment paths are direct edges. The compressed matched
endpoints API supplies their identities without a SearchFlooder. The
quadratic private-dummy clique of the previous formulation is eliminated.

PyMatching's Sparse Blossom avoids an all-pairs shortest-path metric graph,
and its ordinary observable-only decoder avoids recovering explicit paths.
Libra needs the actual graph edges for correlated reweighting and matching
synthesis, so its main edge-output calls still use PyMatching's Dijkstra-style
path recovery. Replacing the auxiliary solver does not eliminate that work.

2. Error configurations versus logical classes
----------------------------------------------

In this one-observable memory experiment, the two logical classes imply
frame flip 0 or 1. The ideal objective is

  P(L=l | s) proportional to sum_{e: D(e)=s, L(e)=l} exp(-W(e)),
  W(e) = sum_{active channels i} log((1-p_i)/p_i).

Core Libra synthesizes lower-weight representative error configurations
for the classes. The enabled degeneracy extension approximates the sum
using retained low-weight cycles around those representatives. A class
containing several moderately likely configurations can beat a class
containing the single most likely configuration.

The algorithm does not enumerate every error or compute an exact posterior.
DetailedResult.log_masses and matching_data.probability are unnormalized
scores; the latter may underflow for large configuration weights. Normalizing
the two log scores gives an approximate class probability, not a calibrated
failure probability. The 20 dB gate can return the original unconstrained
correlated matcher without running the ensemble.

3. Correctness and tie sensitivity
---------------------------------

Both new CTest targets pass: the existing small-hypergraph Libra oracle
linked to the new implementation, and 3000 exhaustive auxiliary assignment
oracles, including odd sizes, zero costs, ties, duplicate pairs, the star
counterexample, and the integer overflow guard.

The old/new implementations were compared on 2176 syndromes per distance:
2048 ordinary and 128 forced-ensemble shots, distances 5,7,...,17. All 15232
predictions agreed; every returned assignment reconstructed its syndrome
and logical parity. Some tied assignments differed while weights agreed
within 1.14e-13 and gaps within 4.55e-13 dB. Degeneracy scores can differ because
the synthesis/cycle history depends on tied representatives.

A separate stress corpus of 32 shots per distance multiplied sampling-channel
odds by 8, retained original decoding priors, and forced the ensemble. One
of 224 predictions differed, at distance 15. Its initial gap was 0.222621 dB;
different starting ties led synthesis to different final configurations.
Both assignments were valid. Stress data are not an error-rate estimate at
p=0.001. Production accuracy was therefore measured again for the new backend.

run, PyMatching and Libra are evaluated on the same configurations.

6. GPU feasibility, hot loops, and B200 capacity assumptions
----------------------------------------------------------

The complete algorithm can be implemented on a GPU. The current C++ code is
a CPU implementation; a GPU port must replace pointers, dynamic containers,
and allocators with indexed arrays and device arenas. Sparse Blossom's
priority queues and contraction/augmentation steps are irregular and
partly sequential within a matching job. GPU feasibility alone does not
establish a speedup or a latency bound.

Straightforward parallel work:
  * Independent shots and the two initial complementary classes.
  * The 60 independent perturbed matching jobs on an ensemble-triggered shot.
    Their outputs must be applied in the original order during synthesis.
  * Independent assignment components; the new sparse auxiliary graph has
    no dummy clique. Tiny subset-DP states can be evaluated by cardinality.
  * Hyperedge weight sums, observable XOR, sparse difference construction,
    incidence/connected-component work, and fixed-base cycle deltas.
  * Independent connected cycle groups and their configuration enumeration,
    with parallel log-sum-exp reductions. Small groups enumerate unique
    spans of rank<10; larger groups use the existing truncated cycle sums.

Candidate-to-candidate representative updates, positive-cycle heap resets,
and the second correlated pass depend on prior results and cannot simply
be run concurrently. Scratch such as edge_position and det_owner must be
private to jobs; sharing the current CPU instance would race.

NVIDIA reports 148 SMs for B200, with 64 warps, 65536 32-bit registers, 32 blocks,
and 228 KiB shared memory per SM, and up to 180 GB HBM. Primary sources:
[NVIDIA SM count](https://developer.nvidia.com/blog/scaling-autonomous-ai-agents-and-workloads-with-nvidia-dgx-spark/)
[NVIDIA occupancy and HBM limits](https://docs.nvidia.com/cuda/archive/13.2.1/blackwell-tuning-guide/index.html)

The following is an unmeasured CUDA allocation plan, not sizeof the CPU
objects or a proven worst-case bound. D=detectors, H=canonical hyperedges,
E=graph edges, R=directed correlation rules, B=ceil(H/8). Graph and prior tables
are shared by instances using the same model and perturbation seed.
32-bit indices/weights, 64-bit time accumulators, and double hyperedge scores
are assumed. The original compact budget is supplemented with an explicit
arena provision for the new auxiliary graph (n<=E,m<=H):

  T =48H+32E+12R+4(D+1)+60*(8H+4E+4R), shared tables.
  W =256D+32E+8R, main matching job scratch.
  A =512E+128H, additional auxiliary arena provision.
  S =124B+8H+8D+32768, per-shot candidate/cycle scratch.
  Parallel 60-member instance =60*(W+A)+S.
  Streaming instance =(W+A)+S.

A deliberately charges the full model's possible auxiliary vertices/pairs
to every matching job, although actual assignment blocks are much smaller
and main/auxiliary arenas could be reused. Its coefficients are design
provisions that must be validated during a port. The bounded small-block
DP's cost/choice/pair tables use about 3.25 KiB, shared by its cooperating
threads. Large graph/queue arrays live in HBM. Sampling/rare-event state
and CUDA context overhead are excluded.

At distance 17, this plan gives 123.087 MiB shared tables, 1741.624 MiB per fully
parallel instance or 31.257 MiB per streaming instance. Reserving 20% of the
decimal 180 GB HBM allows 78 parallel or 4389 streaming workspaces. These are
stored workspaces, not the number that can execute at once.

For a proposed 128-thread matching block using 64 registers/thread and 8 KiB
shared scratch, register allocation limits residency to 8 blocks/SM. A
shared-memory carveout of at least 100 KiB accommodates the blocks and CUDA's
per-block reservation. 148*8=1184 matching jobs can be resident, allowing
floor(1184/60)=19 complete hard-shot Libra ensembles with every member
running simultaneously, or 1184 streaming instances with one active matching
job apiece. Both counts fit the expanded distance 17 HBM plan. The ordinary
two complementary jobs can run together; the fallback is chosen after the
gap is known, so it is a later dependency rather than a third independent
initial job.

Register sensitivity under the same 128 threads per block and 8 KiB scratch design:

 registers/thread  blocks/SM  matching jobs  complete 60-member ensembles
------------------------------------------------------------------------
               32         16           2368                           39
               64          8           1184                           19
               96          5            740                           12
              128          4            592                            9
              255          2            296                            4

The 32-register row requires at least 164 KiB shared-memory carveout. Actual
register use, spills, buffer high-water marks, scheduling of synthesis and
assignment kernels, and memory-access efficiency require a compiled CUDA
implementation. Thus 19 fully parallel or 1184 streaming instances are
conditional design estimates, not measured B200 decoder concurrency.
